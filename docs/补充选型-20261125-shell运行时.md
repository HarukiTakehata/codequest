# 补充选型：Shell 交互运行时四候选实测（2026-11-25）

> 结论先行：**v86 与当前主选 container2wasm 均通过硬门槛**（真实 shell 判题、镜像可定制、启动 < 3 min），可按工程取舍选择：v86 镜像小、许可证干净，适合作默认实现；container2wasm 提供真实 OCI 容器与完整工具链，但镜像约 130 MB、生成物含 LGPL/GPL 组件且本机无镜像构建链。LinuxOnTab 可用但镜像启动 70 s、仓库无许可证；JSLinux 启动快但二进制 WASM 无源码/再分发授权且 rootfs 不可定制；Portabox 启动最快但不是完整 shell 会话（无进程表、无管道、`fork` 不可用），不适合 Bandit 式探索关卡。
>
> 范围说明：四候选对比完成后，已按同一口径**补测当前主选 container2wasm**（见 §3.5）。补测结果：其同样通过全部硬门槛，故本报告的结论从「v86 为唯一可行备选」调整为「v86 与 container2wasm 均可行，按镜像体积/许可证/工具链取舍」。

## 1. 计时口径与证据来源

- 所有镜像 / WASM / JS 资产预先下载，由 localhost HTTP 服务提供，**网络加载未计入启动时间**。
- 指标：`boot_ms` = 运行时开始启动 → 首个真实 shell 提示符；`nav→prompt` = 文档导航开始 → 提示符。硬截止 180 s（>3 min 淘汰）。
- 判题探针：`echo` 回显、创建文件 + `stat`/`ls -l` + `cat`、`ps`/`pidof`/`/proc`、`nc -l` + `netstat -ltn`。
- 每个候选有独立目录 `shell-bench/<name>/`，含 `README.md`（证据表 + verdict）、`result.json`（原始数字）、`run.log`、`screenshot.png`。
- 本报告数字均为**我复核后**的值；各子实例的自报已用父会话另起浏览器标签页/重跑脚本独立验证。

## 3. 逐项证据

### 3.1 v86 — 推荐

- `shell-bench/v86/verify-parent/run.log`：父会话复核 `settled after 4996 ms; status = ready`，`bootMs=4822.8 ms`、`navToPromptMs=4862.5 ms`、`promptText:"~%"`、`promptConfirmedBy:"newline reprint after 2ms"`。
- 13/13 探针：`V86PROBE` 回显、`uname` i686 Linux 6.8.12、`uid=0`、`/tmp/v86probe.txt` 创建 + `ls -l` + `wc -c`=10、`ps` PID1 init + `pidof`、`/proc/meminfo`=104952 kB、`/proc/cmdline` 显示注入的自定义参数、9p 挂载 `host9p on /mnt`、host 注入文件 `v86bench.txt` 内容 `injected-by-v86-host`。
- 端口：`shell-bench/v86/verify-parent/run.log` 的 `probe port_listen` — `netstat -ltn` 显示 `tcp 0 0 0.0.0.0:13 LISTEN`，`/proc/net/tcp` state `0A`，guest 内 `telnet 127.0.0.1 13` 返回 `V86PORT_SERVED`（首次失败因 loopback 默认 DOWN，需 `ifconfig lo up`）。镜像里无 `nc`（278 applets），用 `inetd` + `/etc/services` 替代。
- 镜像定制：`index.html:234` 的 V86 构造器接受 `bzimage`/`initrd`/`cmdline`/`fs9p`；上游 `tools/docker/alpine/Dockerfile`+`build.sh`、`docs/linux-9p-image.md`。父会话实测 `?cmdline=...v86bench=custom1` 出现在 `/proc/cmdline`。
- 注意：镜像无 `stat`/`nc`/`python3`/`gcc`；若用于判题，需按 codequest 设计书 M4 思路自建教学镜像（Buildroot 加 `iproute2`/`procps`/`nc`），而不是用预置 buildroot 二进制。
- 证据：`shell-bench/v86/README.md`（evidence 表 + VALIDATED）、`result.json`、`run*.log`、`screenshot.png`。

### 3.2 LinuxOnTab — 可用但代价高

- 父会话复核：`shell-bench/linuxontab/runs/verify-alpine-parent/result.json` → `boot_ms=70658.1`、`nav_to_prompt_ms=70699.1`、`prompt_text="localhost:~#"`；`runs/verify-linux4-parent/result.json` → `9210.1 ms` / `~%`。与子实例自报 70459 / 8190 ms 一致。
- 端口：Alpine 内 `nc -l -p 8125` 后 `netstat -ltn` 显示 `tcp 0 0 :::8125 LISTEN`（父会话复核输出）。子实例另有一次回环数据往返成功；父会话的 `nc` 回环往返命令超时（隐藏标签页节流/命令串复杂性），故**只把 LISTEN 视为稳定结论**，数据面标为 ⚠️。
- 镜像定制：`shell/<name>.iso` + `site/shell/index.html:888` 的 `ISO_CATALOG`；必须 BIOS/ISOLINUX ISO9660 且 `console=ttyS0`，否则 UI 的 serial0 无输出。
- 阻断项：Alpine 的 ISOLINUX `PROMPT 1` 倒计时在 v86 下不触发且每次按键重置，自动化必须按 ~180 ms/字符输入 `virt`；应用自身 post-boot 脚本会干扰提示符检测；**仓库无 LICENSE**；2.0 页面只外链 `next.linuxontab.com`，代码不在仓库，不算可自托管。
- 仓库内的 `local/skills/shell-ui-agent.md` 是「在 guest 内用 heredoc 写 CGI 页面」的 agent 提示词（busybox httpd + `run.cgi`/`fs.cgi`/`ai.cgi`、6 s watchdog、Fly 端口隧道），**对 codequest 的判题器设计参考价值有限**；可借鉴的是「CGI 执行 → JSON 回传」与超时看门狗，不建议引入为 Hermes 技能（第三方、场景不同）。

### 3.3 Portabox — 排除

- 启动：`shell-bench/portabox/result.json` 3 次 473/488/562 ms（中位 488），`Sandbox.create` 229–263 ms，首次 echo 109–141 ms。
- 有真实 x86_64 ELF 与 Alpine rootfs：`echo`/`cat`/`ls` 正常，自定义 rootfs marker `PORTABOX_CUSTOM_ROOTFS_MARKER=ok` 验证通过；但与判定前置要求冲突：`ps` 仅输出表头、`pidof` 空、`/proc` 仅 `self`、`/proc/self/stat` 空 → **无进程检查**；`sh` 无 pty/stdin/prompt，`sh -c` 一次性执行，`$$`/管道挂死（capabilities `pipelines=false`、`fork=false`）→ **不是可交互 shell 会话**。
- 端口：`sandbox.domain(3000)` 抛 `Error: No route for port 3000`；`create({ports:[3000]})` 静默忽略；`updateNetworkPolicy` 抛 `NotSupportedError`。
- 工程风险：上游 HEAD `npm run build` 因 `tsdown.config.mjs` 重复 `createRequire/require` 语法错误失败；as-shipped 在 Chrome 156 上 `Sandbox.create()` 因 `Uint8Array must not be shared` 崩溃（子实例用 5 行 shim 绕过）；git 历史曾出现 VSCode 文件夹打开 dropper（HEAD 已删但残留 launcher 配置）。0★、2 个月未更新。

### 3.4 JSLinux — 排除

- 父会话复核（独立运行 `node bench.mjs --cutoff 60`）：`result_smoke_parent.json` → `nav_to_prompt_ms=7123`、`vm_start_to_prompt_ms=6486`、提示符 `localhost:~#`。
- 探针：`uname` Linux 6.19.3 x86_64、`JSLINUXPROBE` 回显、`/tmp/benchprobe.txt` 创建 + `stat` 11 B + `cat`、`ps` PID1 init、41 个 `/proc` 进程、`nc -l -p 18080` + `netstat -ltn` → LISTEN。
- 端口对外：guest `eth0` 10.5.41.199/16，host TCP 到该地址:18080 超时；slirp user-net 无端口转发；DNS/外联失败（`wget example.com` → bad address）。
- 不可定制：rootfs 是 vfsync.org 的 9P 懒加载（Revision 11，16492 文件，1.65 GB），无镜像构建器；`x86_64emu.wasm` 仅二进制、无源码/再分发授权，`vfsync` Alpine rootfs 亦不可再分发 → 与 codequest 的自托管/自定义镜像原则冲突。
- 失败源记录：⚠️ `https://bellard.org/jslinux/x86_64emu-wasm.wasm` 下载初期限速（600 s 仅 5.8/20.7 MB），后经分段并行拿到完整文件；⚠️ 本地 `assets/SHA256SUMS` 中 wasm 的 `d22f0b…` 与官方文件实际 `2f41a7…` 不符（陈旧的校验和，勿作为依据）；首轮启动失败的根因是**测试桩**用同步 XHR `responseText` 读 wasm，Chrome 将 1,545,305 B 解码成 1,438,458 B，已改为 `fetch().arrayBuffer()`（`shell-bench/jslinux/assets/bench.js` + `jslinux.js` 的本地 hook），不是 JSLinux 运行时缺陷。

### 3.5 container2wasm（补测，主选）— 通过

- 实例：`shell-bench/container2wasm/`，README + `result.json` + `run.log` + `screenshot.png` + 6 组启动结果；demo 页面/JS/vendor/WASM 全部本地，`serve.py` 提供 COOP/COEP + `application/wasm`。
- 计时：完整探针运行 `nav→prompt=2860 ms`、`wasm→prompt=2280 ms`；另 5 次 `3145/3053/3244/4256/4947 ms`（纯启动 2445–3735 ms）。全部 < 180 s。
- 探针 8/8：`C2WPROBE` 回显；`uname` → Linux 6.1.0 x86_64；`id` → root；`/tmp/c2wprobe.txt` 创建 + `ls -l` 10 B + `cat` 回显；`ps` → PID1 `sh`；`/proc/1/comm`=`sh`；`/usr/bin/nc`、`/bin/netstat`、`/sbin/ip` 存在；`/etc/alpine-release`=3.18.3。
- 镜像：`assets/create-images.sh` 说明任意 OCI 镜像/Dockerfile 可经 `c2w --target-arch=amd64` 转 WASM 并按 50 MB 分片；运行参数 `?args=sh` 实测覆盖 entrypoint；本机无 Docker/c2w，**未做端到端重建**，此项按上游构建链判定可行。
- 端口：guest 内 `nc -l -p 18090 &` → `netstat -ltn` 显示 `0.0.0.0:18090 LISTEN`、`LISTEN_RC=0`；但 demo 页只有 Fetch 代理/`net=none`，无 host→guest 映射（需另写 `c2w-net --listen-ws -p` 页面）。默认 `net=browser` 下 guest `wget example.com` 经代理返回 503（本沙箱 Fetch 失败），启动也从 2.9 s 增至 15.9 s。
- 风险：核心仓库活跃（Apache-2.0），但 demo pin 停在 2024-03；生成镜像捆绑 Bochs LGPL-2.1、Linux GPL-2、GRUB GPL-3、BusyBox GPL-2，分发义务比 v86 重；约 130 MB/实例。因为 xterm-pty demo 关闭 ICRNL，判题器不能用简单字符串写入模拟 Enter，本复测改用 CDP 真实键盘事件，实施方案需自带可靠输入适配层。

## 4. 对设计书的建议

1. 把 v86 从「性能瓶颈明显，仅备选」改为「**实测 4.8–12.7 s 到提示符，性能可接受；作为 Shell 交互层的默认实现候选**」。同口径 A/B 已完成：container2wasm `net=none` 2.9–4.9 s（Fetch 代理模式 15.9 s），两者都远低于 180 s；差异主要在体积、许可证与构建链，而非启动速度。
1a. 主选 container2wasm **保留**，但实施前需解决三件事：镜像构建链（Docker + `c2w` 不在当前环境）、约 130 MB 静态资产的复用/缓存、生成物 LGPL/GPL 组件的分发合规；判题输入层需按真实键盘事件设计（xterm-pty demo 关闭 ICRNL）。若这三点成本过高，直接采用 v86 + 自建 BusyBox 镜像更省事。
2. 若采用 v86：教学镜像必须自建（Buildroot + `procps`/`iproute2`/`nc`），否则 `stat`/`nc` 缺失会让状态检查题写不出来；9p 注入可直接承担 `RunRequest.files` 的课程快照语义。
3. 端口类关卡：四候选都只能稳定承诺「**容器内 loopback 监听 + netstat 检查**」；对外端口均需外部 relay 或不提供，维持设计书 v0.3 的保守承诺。
4. 不引入 Portabox / JSLinux / LinuxOnTab 作为主线运行时；LinuxOnTab 仅保留为「长启动、无许可证」的反面参照。

## 5. 复现

```bash
# 各实例目录都有 README.md / result.json / 截图
cd /workspace/shell-bench/v86       && python3 -m http.server 8101 --bind 127.0.0.1 & node probe.mjs --out-dir verify-parent
cd /workspace/shell-bench/linuxontab && python3 -m http.server 8102 --bind 127.0.0.1 --directory site & python3 bench/bench.py --iso alpine.iso --out verify-alpine-parent
cd /workspace/shell-bench/jslinux    && python3 serve.py --port 8104 --offline & node bench.mjs --cutoff 60 --out result_smoke_parent.json
# Portabox 见其 README（需要 COOP/COEP + shim）
cd /workspace/shell-bench/container2wasm && python3 serve.py 8105 &
node bench.mjs --cutoff 180 --out result.json --log run.log --shot screenshot.png
for n in 1 2 3 4 5; do node bench.mjs --cutoff 60 --only shell --out run$n.json --log run$n.log; done
```
